# DSH for Android v0.6.5

A regression fix first, because it blocked the one thing the app exists for. Then: text comes
back when a send fails, Exit was renamed because it was lying, and there is a way to restart a
wedged connection.

## Questions could not be answered

Every answer you gave an agent was **silently discarded**, and the card vanished first, so it
looked like it had worked.

The cause was a check added to stop a different bug — a replaced question-wait outliving its
socket. That check decided *whether to send* from the same signal it used to decide *whether this
wait is still mine*, and the answer path cleared the slot before completing the wait. So the wait
woke, found its own slot empty, read that as "I have been replaced", and returned without posting
anything. The host never heard, and kept the agent blocked.

The two questions are now separate: replacement, host withdrawal and stop hand a wait back with
nothing to deliver, while a reader's answer and a skip deliver. Ownership still guards the card,
so a replaced wait cannot take down its replacement's card — it just no longer decides delivery.
The handler also releases its slot in a `finally`, so a cancelled socket cannot leave a wait
behind for a later tap to complete into nothing.

What made this hard to see: the JVM harness has no socket, so nothing in the suite could observe
that no post was made. It was visible only in the phone's own log — the same pending waterfall
re-announced four minutes after the tap, with no attempted post and no refusal.

## A failed send hands your text back

Sending into an existing session skipped the restore no matter what failed. The flag that
governed it was only ever set for the first send off the pending seat, so a 504, a refusal or a
timeout took the text and left it nowhere.

The flag is gone rather than flipped, because the failure path is a single sink for every shape.
Two other ways to lose text closed with it. And the restore rule is untouched: it will not
overwrite something you have typed since, and it will not refill a box you emptied by undo.

The message you see changed too. A 504 used to paste four hundred characters of the web server's
HTML; it now says **"HTTP 504: the host did not answer; its web server replied instead"**, and
adds "Your message is back in the composer" only when it actually was. A refused prompt is now
logged; before, it left no trace at all.

One honest caveat: a 504 proves the *reply* was lost, not that the host did not accept the
prompt. Re-sending after a restored 504 can duplicate a message that was delivered.

## Exit was called Close

"Exit" finished the Activity and nothing else — the connection, the event socket and the
notification service all stayed alive, which is deliberate, so an agent that needs a human still
reaches the phone after the UI is gone. The label promised something the control never did.

It is now **Close**, and says so: *"Only this screen closes. The connection stays open, so the
agent keeps working and a question waiting for you is not cancelled — reopen to see where things
got to."*

## Restart connection

There is now a way out of a wedged connection that is not a force-stop. About → Connection has
**Restart connection**, which tears down the multiplexer, the event socket, every resolver fault
and hold, the cached route and the probe cooldowns, then dials both doors again and rebuilds the
streams, the roster, the session and the terminal attachment.

What it deliberately keeps: the cookie jar, your config, per-session drafts, staged attachments
(merged back by id, so an upload that finished mid-restart keeps its receipt), and the attention
centre's pending approvals and questions.

Three things had to be fixed to make that safe, and they were worth having on their own:

- **The mux wiring no longer leaks.** Four collectors were launched with no handles and re-launched
  on every route move; they now have handles and are cancelled. The same fix applies to ordinary
  route moves and to signing out, not only to restarts.
- **A restart does not drop a waiting approval.** The attention centre reattaches to the new
  socket while keeping its cards, and the host's fresh announcement reconciles them.
- **Question waits gained the ownership rule approvals already had**, which is what the regression
  above then had to be separated from.

## Notes

1033 tests across 115 suites. The regression at the top of these notes shipped in `0.6.4` and was
found by the user, not by the suite — its cause was two behaviours sharing one signal, and nothing
in the harness could observe the consequence. The lesson is in the code comment now, not only
here.
