# DSH for Android v0.4.0

A scrolling release. The transcript was rebuilt on a different layout, and most of a
week went into finding out *which* layout, from the phone rather than from an argument.

## Scrolling was rebuilt, not patched again

The transcript rendered with `reverseLayout = true`, so the newest row pinned itself to
the bottom without the app ever scrolling. That is a real benefit, and it came with a
price nobody had written down: a reversed list anchors on the item at the **bottom** of
the viewport and lays the rest out upward, so an item's bottom edge is fixed by the rows
below it.

Measured in a harness before anything was changed — a 48px row grown to 200px, in a
300px viewport:

| layout | what the row's top edge does |
| --- | --- |
| `reverseLayout = true` | rises by **exactly the 192px it gained** |
| ordinary list | **does not move at all** |

So "opening a section throws it off the top of the screen", "it closes the rows I'm
reading" and "it jumps about" were one property of one flag, and the six mechanisms
stacked on top of it — a stick flag, a frozen live row, a measured row height, a held
fold set, a per-scroll-position `scrollToItem`, an oversize teleport — were patches over
that property.

The transcript is now an ordinary, top-anchored list with **one** thing that moves it,
`ui/scroll/TailFollow.kt`, which is nine tests and one file:

- **New rows** are followed when the reader was already at the tail, and the move
  watches *how many rows are below the fold* rather than the row count — a target
  captured when the count changes goes stale the moment a second row arrives, and the
  animation held the very flag that would have retried.
- **Growth inside the tail row** — a streaming answer — is corrected by exactly the
  number of pixels it is cut off by. Self-limiting: the correction can never exceed the
  overflow that caused it. A message taller than the window is not chased at all, which
  is the rule that stops "how far it is cut off by" becoming the height of the whole
  message: measured on the phone, corrections of **3,625px**, each replacing every row
  on screen.
- **A finger on the list stops all of it.** `isScrollInProgress` is not enough on its
  own — it turns on when a drag passes touch slop, so the window between a finger
  landing and its first movement reads as idle.

Opening a row now keeps its top edge and grows downward, because that is what a
top-anchored list does. Confirmed on the device with real rows, not the live one:
`e31083` grew 693px, `e31089` 423px, `e298` 271px, `e4740` 4,684px — and the list did
not move for any of them.

## The app stopped moving lists nobody asked it to move

- **The drawer remembers where you left it.** It used to `scrollToItem(0)` on every
  open, and before that to page itself to the open session; the position it was
  discarding was already being remembered, so the reveal was destroying the one thing
  that worked. It opens at the top until you have chosen a position, and at your
  position after that.
- **The drawer holds its order while it is open.** A roster refresh used to re-sort
  sessions by `updatedAt` under the reader — recorded as shifts of two and three rows
  with only 85–95% of the visible rows surviving. Membership is deliberately *not* held:
  a stale row is worse than a moved one.
- **Conversation display is honoured.** `ui-chat.transcriptView` was displayed in
  Settings and then ignored, so a host set to **Normal** — which is documented as never
  folding — still had its completed turns collapsed. It was read only when the Settings
  sheet was opened; it is read on connect now.
- **A turn whose rows are on screen is never folded**, however you got there. At the
  tail, the turn that has just ended is exactly the one under your eye when its closing
  message lands.

## It got measurably smoother

Frame times, from the device, over 24,053 frames with the reader scrolling:

| | before | after |
| --- | --- | --- |
| frames over the 11ms budget | 11.7% | **5.4%** |
| frames over 33ms | — | **1.4%** |

What was actually costing the frames:

- **Every visible row recomposed on every streamed token.** The row model is a sealed
  interface of data classes holding lists and a `JSONObject`, which Compose cannot prove
  anything about, so nothing could be skipped. Measured: changing an *off-screen* row
  recomposed all seven visible ones. `@Immutable` on `ChatEntry`, `DisplayRow`,
  `LiveAttempt`, `TodoItem` and `MessageAttachment` is the promise that fixes it —
  measured after: zero.
- **Every token re-parsed the whole answer.** 1.5ms for a 2.4KB message, 3.9ms for an
  18KB one, sixteen times a second. Parses are cached now, and long ones happen off the
  main thread.
- **The rail built a preview of every turn's prose on every token** — joining hundreds
  of kilobytes, for a card that exists only while a finger is on the rail.
- **The drawer's dots animated while the drawer was shut.** The sheet stays composed
  while closed, so a running session's chase rendered at the display's rate for a sheet
  nobody could see.

## Everything else

- **Arriving at the bottom and jumping to it are deterministic.** Both used to target an
  index captured before a move that could be overtaken by the next row.
- **Bash rows wrap** rather than panning sideways, both the command and the output — and
  only the visible output lines are composed, which was a thousand `Text`s per row.
- **Opening a parent session settles its subagents' alerts**, and a subagent's own
  "done" notification is silenced. A question, an approval, an error or a bell still
  speaks for a child: a stalled child is running as far as the parent's header count is
  concerned, which is the one thing you cannot see from up there.
- **The whole subagent bar goes up**, not just the words in it.
- **Closing the last shell returns to the conversation.**
- **Settings pages its archived list**, like the drawer already did.

## A harness, so the next one of these is not an argument

Scrolling was the one behaviour no unit test could reach and no reader could describe
precisely, so it has one now: a real Compose layout, real touch input and real geometry
on the JVM under Robolectric, in seconds, with no device. Getting there needed a false
`$HOME` (Robolectric caches under a user home the build sandbox mounts read-only) and an
`Application` of its own (the real one builds a `ConfigStore` on AndroidKeyStore, which
Robolectric has no shadow for).

Alongside it, a latent recorder in the app itself — `docs/SCROLL-DIAG.md` — which draws
nothing, consumes no event and never scrolls anything, and which is how every claim
above was checked. **342 tests**, all JVM.

## What is not verified

- **The drawer's restore waiting for a finger to lift** is the last change in this
  release and has not been seen on a device: it needs the drawer to be opened.
- **The bash wrap** is the second-newest change. Its cost profile is reasoned from the
  recorder, not measured against the panning version.
- The emulator remains unusable for this app — its install has no host login and the
  credential store is bound to the device keystore — so every device claim here comes
  from the phone's own recorder, not from a driven emulator.
