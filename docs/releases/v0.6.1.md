# DSH for Android v0.6.1

A day of fixing what using the app actually turned up. Most of these were found by a person
looking at a screen or a log, not by the suite — and two were found by reading the host.

## Keeping the LAN route

The app reached the host over a LAN route when on the same network and a public one
otherwise. Returning to Wi-Fi never brought it back, not after minutes and not after hours.

Two holes, and the second is why time did not help. `onAvailable` can fire before a returning
network is actually routable, so the probe that landed there failed — and because ordinary
traffic only consulted a **cached** resolution whose TTL nothing checked, nothing ever
re-probed. One early failure was permanent. Separately, the resume path re-checked the socket
and re-subscribed streams but never revisited the route, so it reconnected onto the cached
public winner.

Four connectivity callbacks are now observed instead of two, reduced to **rising edges only**
so a signal-strength re-publish costs nothing and the listener cannot become a timer; and a
foreground resume forces a fresh probe.

**And a door that fails no longer stays failed forever.** Failure is now split by kind: a
**transport** error is a fact about the wire, held briefly and then re-admitted on a growing
pause (5s, 1m, 5m, 30m), with at most two resume-driven retries per run of failures; a **wrong
answer** — a body that is not a DSH envelope — is a fact about the door, and a captive portal
will answer a fresh probe exactly as it answered the first, so that verdict holds until the
network itself changes. While a door is set aside, About says so and says which kind it was.
Previously one transient failure could strand the app on the public route for the life of that
network, which is what "not very robust lately" was.

## Approvals

Accepting an approval **cleared its own card before anything was sent**, and the reply was
never inspected — a refused answer rendered as accepted, with one `Log.d` line as the only
trace. Then the first fix waited for the host's `cancel`, which turned out never to arrive:
the gateway removes the answering client from the delivery set *before* it builds the cancel
recipients, so on a phone that is the only client the recipient set is empty, in every path.

An accepted answer now clears on the host's **own accepted reply** after a short settle
grace, reconciled against the roster the host re-announces on every new event stream, and
still on a `cancel` if one ever comes. A tap first moves the card to *Sending…* with the pills
genuinely inert; a refusal says so on screen, re-arms the pills and re-posts the notification.
Nothing clears before the reply, and nothing withdraws the notification while an answer is
unconfirmed. The question path is unchanged and still optimistic — recorded as open work.

The card's status line is now a fixed-height strip that is laid out in every state, so the
copy cannot move the card, and a 24-character budget is test-asserted so a future edit cannot
reintroduce the reflow.

## Reading the queue, at last

Editing a queued message had been impossible for months, and the cause was not in the app:
the host moved the pending queue into the **`inbox` session projection** and stopped sending
the `queues`/`queue` frame the client read. The Edit control was always there, permanently
disabled, behind a condition that no longer held — and a local echo drew the same glyph with
every verb inert, so it looked like a feature that had never existed.

## Start-up

The loading screen showed the mux's **debug log** verbatim — `item s2 snapshot (#1)`, where
`s2` is a stream id handed out in collector-scheduling order and so means something different
per run. A log statement built for logcat was the user interface. It now shows five real steps,
each naming the host as what is being waited on, with the app's own `StateDot` as the throbber
and `ProgressBarRangeInfo.Indeterminate` so a screen reader never hears a percentage.

## Landing on the right session

A fresh open landed on an **automation run**. The autopick took the most recently *updated*
non-subagent row, and scheduled runs are updated constantly — so it won whenever the reader's
own session was older than the last run. Replaying the old rule over a live roster: at 3, 6,
12, 24 and 48 hours idle it picks a run every time. It now skips runs and subagents, reusing
the drawer's own predicate so the two cannot disagree, and still falls back to a run when
nothing else has content. A reconnect keeps the session that was open; only a cold start picks.

## Family tokens

The usage popup now totals a session's whole family — subagents and their subagents — with
each member priced at its own route. Three findings shaped it. Per-child usage **is** reported,
but **669 of 1,287** live subagent rows carry none, so the panel always states its coverage
(`3 of 4`) and says how many were not reported. A **forked** subagent's log is seeded with its
parent's prefix and the usage projection has no reset at that cut, so a naive sum counted
inherited history twice — measurably **79%** of one real total. Two candidate detectors for
forked children were built and **both killed by measurement** (116 and 4 false positives on the
live roster), so rather than guess, the panel is labelled **"Family, as reported"** and says
plainly that a forked child's history is counted twice. Cost is withheld entirely if any member
has no published price, because a money-shaped subtotal is worse than no number.

## Smaller things

About now names the **connected host's DSH version** — or says "Not reported", because on
0.2.0-rc.2 it is nowhere on the wire: not in the `ready` frame, not in any of the 140
descriptors, not on any HTTP route, and the host's own web client renders a build-embedded
literal rather than asking. Adding `version` to the host object in `registerRemoteEvents` makes
the row real with no app change. A widget title cap no longer truncates at 32 characters before
the view truncates it again, and the provider asks for 140dp rather than 90dp.

## A note on testing

814 tests across 86 suites. Four of the bugs fixed here were found by a person looking at a
screen, and one by reading the host's source: a negative forty-six-year age, a card with a
centred column, an Edit that could never be enabled, an approval that cleared itself before
asking, and a cancel that is structurally never sent to the client that answered. Every one
passed the tests that existed when it shipped.
